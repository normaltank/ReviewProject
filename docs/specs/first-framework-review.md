# 首轮条款审核体验：已确认开发规格

> 状态：业务范围已确认，三票代码已本地集成验收，独立审查发现已复核关闭；用户本人首次体验与正式效果验证待做。脱敏规格见[GitHub Issue #1](https://github.com/normaltank/ReviewProject/issues/1)，交付版本、实际验证与Issue状态见[任务图](first-framework-review-tasks.md)及[交接状态](../STATE.md)。
> 需求依据：2026-11-09业务访谈Q1—Q13及其整体确认、现有项目计划、术语表与ADR-0001。
> 以下需求、问题描述与实现/测试决定保留规格冻结时语境；它们不是当前实施状态或效果已验证的声明，当前结果以交接状态为准。

## Problem Statement

出版社希望理解外审评分与Comments背后的评价观点和判断尺度，并据此持续改进现行审稿Framework。负责标准的人需要看清某条要求为什么值得保留、修改或补充条件，同时兼顾重要质量问题、作者负担与审稿效率。

现有原型能保存原文和原分、接收观点候选、人工修正观点，以及保存操作者填写的条款对照和提案。它还不能从一批记录中完整发现值得审核的条款问题、联合多来源证据形成候选改法，并让用户方便地保存条款审核决定。已有案例不等于这条自动分析链路已经实现。

## Solution

在现有本机可信编辑工具上补一条完整路径：

小批真实B审稿记录 → 有出处的独立评价观点 → 候选概念及原分关联 → 与A现行内容或候选条款对照 → 值得审核的问题及有依据的候选改法 → 用户查证、纠正和记录决定 → 保存后可重新打开。

每个条款问题同时展示原规则及其效力状态、相关观点与原话、评分关联的性质、支持和反对材料、适用条件、未知项、候选改法及排序理由。来源可查、判断已核实、修改被采纳、修改效果得到验证分别记录。

首次体验由用户本人完成。先检查错漏、原文是否好找、是否帮助完成审核并减少翻找整理的负担；计时和结果整理由统筹负责。正式标准的长期效果另行验证。

## User Stories

1. 作为标准负责人，我希望明确本批使用哪些审稿记录和哪些现行条款资料，以便知道结论覆盖范围。
2. 作为标准负责人，我希望看到原始分项标签、分数和缺失原因，以便分析时不丢分、不改分。
3. 作为标准负责人，我希望一段评语可以拆成多个独立观点，以便分别理解不同判断和修改要求。
4. 作为标准负责人，我希望每个观点可以回到准确原文，以便核查系统是否误读。
5. 作为标准负责人，我希望条件、否定、跨句理由、要求强度和替代做法保留下来，以便建议不被擅自升级或收窄。
6. 作为标准负责人，我希望补录遗漏、拆分或纠正观点，以便不受模型初次答案限制。
7. 作为标准负责人，我希望重新运行模型后保留自己的修改和修改历史，以便持续复核。
8. 作为标准负责人，我希望相近观点对应有定义和边界的候选概念，以便跨记录比较有稳定含义。
9. 作为标准负责人，我希望同主题下相反的判断仍然分开，以便看见真实分歧。
10. 作为标准负责人，我希望看到某观点与评分是老师明说的关系、系统推断还是未知，以便不把相关性当给分原因。
11. 作为标准负责人，我希望看到A资料的原始出处、候选整理和正式效力状态，以便不把课程归纳冒充已获批标准。
12. 作为标准负责人，我希望看到哪些观点与当前条款相关、条件不同或在当前材料中未覆盖，以便找到值得审查的问题。
13. 作为标准负责人，我希望系统主动列出有证据的问题候选，以便不必先手工选择所有条款并填写提案。
14. 作为标准负责人，我希望联合查看多份记录的相关证据，并区分记录数、稿件数和教师数的已知情况，以便避免重复计数和多数错觉。
15. 作为标准负责人，我希望同一问题有原规则对照及有材料支持的其他改法，以便比较保留、改写或增加适用条件的取舍。
16. 作为标准负责人，我希望看到各改法的依据、反例、利弊、可能增加的负担与未知项，以便作出有理由的决定。
17. 作为标准负责人，我希望每条新增建议说明材料怎样支持它，以便区分原话、系统推断和编辑建议。
18. 作为标准负责人，我希望已有作者回复可以与老师建议并列，以便了解回应情况；没有回复时明确缺失。
19. 作为标准负责人，我希望系统推荐审核顺序并解释理由，同时能查看全部候选，以便安排有限审核时间。
20. 作为标准负责人，我希望少见但可能影响核心结论的问题单列，以便重要线索不被高频主题淹没。
21. 作为标准负责人，我希望可以纠正整理结果，并记录保留、修改、补材料或暂缓以及理由，以便结果可继续处理。
22. 作为标准负责人，我希望个案处理与通用条款修订分别记录，以便同意某篇论文的做法不会自动变成普遍要求。
23. 作为标准负责人，我希望记录基于哪个材料和规则版本作出决定，以便来源变化后知道哪些决定需要重新检查。
24. 作为标准负责人，我希望保存后重开仍能看到决定、证据和历史，以便继续工作。
25. 作为标准负责人，我希望敏感原文及其摘要、检索结果和派生建议沿用来源权限，以便信息留在获准范围。
26. 作为首次体验者，我希望通过普通界面查证、纠正和记录决定，以便不用手写JSON或文本位置。
27. 作为首次体验者，我希望反馈错漏、查证困难和操作负担，并查看实际用时，以便判断工具是否帮上忙。

## Implementation Decisions

以下是规格阶段提出的实现约束，未表示新功能已完成：

1. **复用现有入口。** 沿用本机可信编辑、浏览器原文复核、受控应用决定和恢复工作区的操作路径，继续使用现有原件冻结、原分保存、观点历史及条款证据校验能力。
2. **增加薄的聚合分析能力。** 在现有单来源工作区之上组织小批记录及规则资料的引用、分析运行和审核决定。原工作区、原始文件和历史结果保留；多来源证据仍逐项绑定来源、观点版本和权限，不能通过绕过原单源提案约束拼接成无来源结论。
3. **绑定实际输入。** 记录所选来源、有效观点视图、运行记录、规则资料及其版本/指纹。不同运行或工作区副本不当成新的独立支持；人工决定基于的材料发生变化时显式提示重新检查。
4. **保留抽取与评分分析的顺序。** 首次理解Comments不提供数值评分、A评价或其他教师结论；之后再连接原分，区分明确理由、推断和未知。不生成缺失的A评分，也不自动改老师原分。
5. **从探索候选推进，不等待全部金标。** 模型和规则结果可作为明确标记的探索性线索进入复核；人工已确认观点、待核观点及机器推断不能混作已验证统计。专业身份与实际执行者另记，不靠记录名称推定。
6. **受控概念与方向分开。** 候选概念保存稳定标识、定义、例子、边界及待确认状态；主题、正负判断、条件和动作分别保留。抽取程序调整、概念词典调整和出版社条款修改各自留痕。
7. **候选发现及改法必须有材料。** 允许系统提出相关条款、条件差异、当前资料未覆盖等线索并形成候选改法。必须展示引用、推理说明和未知项；A原引文仅支持原规则，不冒认草案新增内容来自A。没有反对材料时如实说明检索范围，不编造两方意见。
8. **方法选择受实测约束。** 优先复用已有本地抽取入口，并保留规则对照。每个关键环节只设一个主要方案和一个简单对照；依据真实错误、条件保留及修正成本决定是否换组件，不将工具列表变成安装任务。本规格不强制新增模型、在线服务或向量数据库。
9. **排序可解释、候选可全览。** 根据材料完整程度、核实情况、可能影响和重复出现情况给出审核顺序及理由；可能影响核心结论的少见问题单列。排序不承担学术正确性裁决，也不把频率直接变成标准权重。
10. **审核决定单独保存。** 使用有稳定标识、理由、时间、材料绑定和历史的条款审核决定，区分个案处理、对候选条款的处理及正式授权。页面导出、受控应用成功和正式标准发布是不同状态。
11. **沿用版本边界。** 按ADR-0001保留原审稿要求和历史原分原意见；用新标准比较时另记。首轮记录所用规则资料及其效力/版本状态，不伪造正式版本，不建设正式发布与在审稿件迁移平台。
12. **权限从输入传到所有派生内容。** 首轮优先选取授权范围内的普通意见，在本机可信编辑工作区处理；这不等于普通意见可对作者公开。聚合、检索、摘要、模型上下文、导出和日志均受来源范围约束，不能把作者不可见内容经过改写后变成可见。
13. **缺失与失败可见。** 材料不足、抽取失败、部分完成、证据无法定位与没有发现问题分别显示。人工已改记录不得被重跑覆盖；重试幂等，旧记录仍可查。

## Testing Decisions

### 两个主要测试入口

**入口一：完整数据操作路径。** 从CLI导入合成小批记录，经观点结果、条款问题与候选改法，到应用审核决定、保存后恢复。观察公开操作结果，不以私有函数或直接查询数据库代替对外行为。

它覆盖原分往返、引用绑定、跨记录证据、权限边界、修正历史、幂等与恢复；不证明真实模型理解正确或新规则有效。复用已有原分/观点往返、规则包导入和提案保存测试的行为案例。

**入口二：用户实际操作路径。** 在浏览器中打开条款问题、查看原文、纠错、比较方案、选择处理决定，并通过现有受控入口应用后重新打开。

它覆盖查证与纠正是否可操作、决定是否真正保留、下载与保存是否正确区分；浏览器测试通过不证明专业判断可靠或真实节省工时。复用已有观点表单、原文回链和条款页面测试的方式，补上当前预填提案测试没有覆盖的主动候选路径。

测试范围沿用已提出的两条完整公开操作路径，用户随后授权统筹自动按流程继续；实现阶段据此外部行为验证，不扩展为任意私有函数边界。新增实现按用户可观察行为逐条进行红—绿验证，再执行项目既有回归；不先堆积一批镜像内部实现的测试。

### 必须覆盖的行为与真实体验记录

- 使用合成输入验证：一段多观点、跨句理由、否定、条件与替代动作、同主题相反判断，均能保留原文关系或明确待核。
- 无法确认条件含义时保存原话和未知状态，不擅自补成必须完成某项动作。
- 原始分数、空值原因、私密分区和人工修改在重跑、保存、恢复后保持；重复副本及重复运行不增加独立支持数。
- 每项建议的支持/反对引用可定位；不存在的来源、错误片段、越权引用或已失效材料不能悄悄作为当前有效依据。
- 未取得完整A标准时，“当前候选资料未覆盖”不能变成“A没有这项要求”；缺A评分或教师交叉数据时停止相应分数差异/严宽推断。
- 个案决定不自动发布通用标准；对草案作出处理不自动变成论文事实核验或标准效果证明。
- 在隔离的本地真实材料副本上运行当前主要模型和规则对照，保留实际输出、错漏、条件/强度改变、待核项及修正成本。没有独立金标时只报告探索结果。
- 已用于开发的案例继续标为已知回放；若需要独立效果结论，另外选未参与调试的材料，不以文件副本数代替独立稿件/教师数。
- 用户首次体验记录查证、纠正及作出处理决定的过程和实际时间，区分用户体验反馈、代理演练、专业语义核实和独立新旧标准试评。
- 未做可比人工对照时只报告观察用时与用户反馈，不宣称节省某个百分比；未验证规则后果时不宣称减少返修或改善学术质量。

## Out of Scope

- 一次建设完整审稿平台、替作者自动写论文修改意见或直接替人决定录用。
- 自动发布正式标准，或因用户首次体验就确认全部A候选条款具有正式效力。
- 缺少真实交叉结构时估计教师严格程度、论文真实质量或具有代表性的群体结论。
- 首轮证明所有学科适用、建立全国高校教师总体评价模型，或以主题高频自动形成通用条款。
- 继续扩展通用Word解析器、强制安装全部候选工具、无实测依据更换技术栈。
- 未经授权的数据外发、付费模型调用、破坏性操作、远端发布及作者端导出。
- 重写历史原分原意见，或本轮直接迁移在审稿件的正式标准。

## Further Notes

本地已有A课程材料及局部候选整理，但正式版本、完整评分锚点和同稿A评分尚未在限定核查中取得；已核的B工作区仍缺稳定教师标识及完整交叉关系。这些限制需要在结果中展示，不阻塞B侧观点理解和候选条款审核体验。

用户已允许把本地匹配论文先作为老师所评论文来推进工程；这是工作假设，不伪造发送记录或事后版本确证。作者已经写过局限也不自动抵消老师要求，应将原文及老师建议并列供审核。

本地草案用于下一步核对测试范围和拆分任务；原始业务材料、身份、密钥和私密评语不进入公开工作项。任务应按完整业务路径拆分，每项都有独立可演示的结果及真实阻塞关系，不按数据库/算法/页面各建一张孤立任务。
