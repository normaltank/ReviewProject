# Engineering workflow

本项目采用 Matt Pocock 工程技能的工作方式。按请求所在阶段选择技能，沿用其确认节点和完成条件。

## 从需求到实现

1. **取得上下文**：读取入口文档、相关 GitHub Issue 的正文和评论，以及领域文档。已有明确规格时直接从对应阶段继续。
2. **澄清需求或设计**：需要收敛方案时使用 `/grill-with-docs`，将确认后的术语和设计决策通过 `/domain-modeling` 按需记录。
3. **形成规格**：基于已讨论的需求调用 `/to-spec`，明确用户可见的行为、测试边界及范围，按该技能流程发布规格 Issue。
4. **拆分任务**：调用 `/to-tickets`，拆成可以独立演示或验证的完整小任务，声明真实阻塞关系；确认粒度和依赖后发布。
5. **处理工作项**：调用 `/triage` 核验问题、整理分类和状态、形成足够明确的执行说明；从没有开放阻塞的任务开始实现。
6. **实现与验证**：围绕工作项的验收行为完成变更；需要测试驱动时使用 `/tdd`，需要探索交互或状态模型时使用 `/prototype`。验证范围与变更风险相称。
7. **审查与交付**：使用 `/code-review` 按明确基线检查项目规范和规格符合性；撰写 PR 时使用 `/pr`。需要持续跟进已有 PR 时，由用户调用 `/autopilot`。

这些技能按阶段配合，不要求每个小改动完整重跑全部步骤。存在不确定的技术路线时，可使用 `/wayfinder` 组织探索型任务；模块接口或架构问题按需使用 `/codebase-design` 和 `/improve-codebase-architecture`。

## 本地资料与公开工作项

`Afeedback/`、`Bfeedback/` 和 `EssayCourse/` 是本地研究资料目录。当前公开仓库跟踪工程配置和后续经选择的源码；这些资料目录由 `.gitignore` 保留在本地。

引用材料时区分原始证据、机器处理、人工核对与分析推断，保留相对路径、页码或时间戳及必要的文件哈希。公开工作项采用必要的去标识化说明；发布具体原始材料以用户指定的内容和范围为准。

## 本机 GitHub CLI

安装并登录标准 `gh` 后可直接使用技能文档中的命令。本机也提供 `scripts/gh.ps1`，支持调用便携版 GitHub CLI 和复用已有 Git 登录；具体约定见 `issue-tracker.md`。
