# Engineering workflow

本项目采用 Matt Pocock 的阶段方法，由主代理作为唯一统筹接单。用户用自然语言描述目标即可；统筹按项目级 [reviewproject-coordinator](../../.agents/skills/reviewproject-coordinator/SKILL.md) 执行本页方法，需要委派时按[多代理协作](multi-agent.md)派工。子代理只执行获派阶段。

## 任务分流

按[根入口](../../AGENTS.md#按任务读取)读取当前任务相关资料；有关联 Issue 时读取其正文及评论，操作前遵守 [Issue tracker](issue-tracker.md)。沿用已确认的范围、业务决定和测试边界。统筹说明所选路线与完成条件；文件数或代理数不单独决定规模。

- **业务含义或范围不明**：研究现有证据，形成具体场景、选项和建议。重大未决业务问题由统筹集中向用户提问；继续推进不依赖答复的工作。术语和设计决定按领域约定按需记录。
- **一个可独立验收的代码结果**：明确范围、验收和验证边界后，交给一名实施代理。按风险验证，固定基线审查，再交付。
- **多个分别验收的交付项或跨上下文实施**：进入下节完整阶段，实际安排实施、串行集成和双轴审查。
- **纯文档、配置或导航维护**：采用轻量文档路线，可由主代理或一名指定写入代理使用现有 checkout；其余参与者只读。检查内容、配置格式、链接和改动范围，只有涉及运行行为时才执行相应运行验证。
- **缺陷或原始工作项**：核实可复现行为、证据、缺失信息和 [状态标签](triage-labels.md)，形成可执行范围后选上述路线；明确的规格和任务直接续接。

## 多交付项的阶段与产物

1. **规格**：写清用户问题、可观察行为、范围、非目标、验收和测试边界。统筹提交可审阅的具体方案，将影响业务行为、测试边界的未决决定交用户确认；已有确认直接沿用。完成条件是实施者可从同一规格理解交付结果。
2. **任务图**：沿完整业务路径拆票，每票可独立演示或验证，覆盖该路径所需的数据、接口、界面与验证；机械迁移可按兼容步骤拆分并说明理由。标明真实阻塞，核对无依赖环。统筹提交粒度与依赖方案供用户判断；确认后在已授权发布范围内记录到 GitHub Issues。
3. **就绪与实施**：核实任务范围、验收、已满足依赖和隔离资源。把各票交给实施代理，使用独立分支和 worktree；有资源且互不冲突的任务并行。交接字段和同步要求见多代理协作。
4. **集成**：由独立 merger 一次接收一份成果，串行写入集成分支，核对提交及验证证据并验证受影响行为。前置成果已集成且验收通过后才释放下游依赖。
5. **审查与返修**：固定比较基线与集成版本，分别派出只读 Standards、Spec 审查代理。发现集中交给一名实施代理统一返修，经 merger 集成后补充验证并由相应审查者复核；未采纳的发现记录理由与复核结论。
6. **交付**：统筹逐项核对规格、每票产物、集成记录、实际版本的验证及两轴审查；按现有授权处理 Issue、PR 和远端动作。缺少的环节明确标为未执行。

常规技术选择及已授权步骤自动推进。业务决定、测试边界和拆票粒度的人类判断由统筹呈交具体方案，不要求用户记技能命令；需要提问时只集中询问尚未决定的部分。

## 项目阶段方法与全局技能

项目技能直接承载上述阶段方法。全局 `to-spec`、`to-tickets`、`triage`、`implement`、`implement-spec`、`ask-matt` 等技能保持 explicit-only：项目文档和自动技能不直接自动触发它们，也不修改其调用策略。用户显式调用原技能时，先读取其实际 `SKILL.md`，遵守原确认节点，并沿用已有明确确认。

按任务需要使用可用的工程能力：复杂故障读取 `diagnosing-bugs`；测试驱动开发读取 `tdd`；交互探索读取 `prototype`；模块接口设计读取 `codebase-design`；代码审查读取 `code-review`；撰写 PR 读取 `pr`。这些技能的实际指令适用于调用它们的任务；本页不替代技能原文。持续跟进 PR 或循环任务由用户明确安排。

## 验证与完成条件

代码围绕已确认的外部行为验证；修复保留原失败样本并检查受影响的既有行为。按实际风险选必要检查，界面或数据操作补充对应验收。纯文档配置检查其格式、引用与执行边界，避免制造应用测试或虚构多任务实施。

代码交付的 Standards 与 Spec 独立检查规范和需求，使用同一固定基线、受审版本、需求与规范来源。单任务按风险确定验证深度；纯文档可做内容与配置审查，明确实际方式。报告必须能区分配置完成、委派完成、审查完成和实施完成；“已派出”或代理一句“已完成”不代替成果验收。

最终说明实际变更、对应版本或未提交状态、验证结果、两轴审查是否执行及剩余限制。有提交或远端交付时核验准确版本与必要检查；仅配置流程不代表真实多工单流程已端到端验证。达到当前任务验收点即停止。

## 本地资料与公开工作项

`Afeedback/`、`Bfeedback/` 和 `EssayCourse/` 是本地研究资料目录，由 `.gitignore` 保留在本地。引用材料时区分原始证据、机器处理、人工核对与分析推断，保留相对路径、页码或时间戳及必要的文件哈希。公开工作项采用必要的去标识化说明；发布原始材料以用户指定的内容和范围为准。

本机可使用标准 `gh` 或 `scripts/gh.ps1`；仓库确认和操作方式见 [Issue tracker](issue-tracker.md)。
